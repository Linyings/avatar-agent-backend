# 通用模式请求升级与模型切换后的恢复

日期：2026-10-18。仅本地部署，未发布生产。

## 问题

PC 通用模式请求只以 `generate-narration-script.general-v2.plan-N` 等阶段编号标识调用。新包修改请求 revision 或输入后，继续旧工作流会撞上旧步骤的请求指纹，返回 HTTP 409 `workflow_input_mismatch`。原流式请求指纹也未包含后端实际解析到的模型配置。

当前本地配置为 Pro `glm-5.3-flashx`、Flash `glm-5.3-flash`。故障任务凌晨三次模型结果已经记录为 `glm-5.3-flashx`；本次不能归因于刚从 DeepSeek 切到 GLM。修复同时覆盖后续服务端更换实际模型。

## 修改

- 仅对 PC、script_draft、narration_outline、general-editing-v2 合同，以及明确的通用模式阶段编号生效。
- 实际子步骤编号附加请求摘要，摘要覆盖请求内容、合同 revision，以及通过与 Stream 相同逻辑解析到的模型档位、模型名、服务地址、thinking/reasoning 和 temperature。
- 保留工作流及父步骤编号，继续复用上游检查点；保留旧执行记录和计费归属。旧格式请求自动迁移到新版子步骤，不需要 PC 重打包、重新登录或删除项目。
- 相同内容和配置生成相同编号，沿用既有租约、结果重放和计费去重机制。内容/实际模型改变则新建子步骤，原请求指纹校验仍保留。密钥轮换及未选中的模型档位变化不触发重新执行。
- 在工作流行锁内检查该逻辑阶段的其他版本；仍在运行、过期但结果不明、明确 workflow_result_unknown 或未确认的提交会阻止新的付费执行。跨用户、客户端及输入身份校验保留。
- 已完成上游内容不会仅因切换模型被强制重生成；需要重做已完成阶段时仍使用“从指定步骤重新执行”。
