## 实测证据

在 WSL2 的 API 容器内用 ffprobe 读取七个 `p*/audio.wav` 文件，与接口中 `segments[].duration` 一致：

| 段落 | 音频秒数 |
|---|---:|
| p1 | 5.503125 |
| p2 | 19.500250 |
| p3 | 11.041125 |
| p4 | 18.599208 |
| p5 | 14.071333 |
| p6 | 15.905708 |
| p7 | 8.916500 |
| 合计 | 93.537249 |

最长单段 19.500250 秒，累计超出整片 90 秒上限 3.537249 秒。`steps[].seconds` 为执行耗时，没有参与配音时长校验。七段 TTS 均成功；失败发生在所有段落结束后的整片校准。

## 原因与修复范围

90 秒源自 PRD 的首版成本和复杂度控制，适用于整片，不代表模型或架构只能处理 90 秒。v3 继承了旧执行器的这一限制；本次没有改变此产品限制，也没有改写、截断用户文案。

旧条件将零时长与超限归为同一错误，且未显示累计时长，还要求新建运行并提供普通重试按钮。现已拆分有效时长校验与整片上限校验，保留原 0.05 秒舍入容差。新错误按 F04 整体标记，保留每段成功记录和音频。

项目快照新增 `audio_timing`，由已保存音频时长派生，提供段数、累计时长、最长单段、整片上限和可操作错误；兼容旧失败提示，不修改历史运行。状态卡显示累计值，超限时打开现有文案编辑器，经现有修订提案流程确认后再制作。文案确认阶段提前显示上限，配音阶段显示已完成部分累计时长。没有根据字数做不可靠的硬拦截。

对未修改的超限运行，Agent 的 retry/resume、启动入口和 HTTP retry 均不再启动无效工作；底层重试事务也拒绝该状态。用户仍可按明确意图修改文案或提出新的产品时长需求。

## 后续产品决定：取消累计时长上限

2026-11-08，用户明确要求视频可以超过 90 秒或更长，取消该限制。以上章节记录此前排查与修复，不代表当前产品规则。

删除累计时长上限、重试阻断、目录接口的 `max_duration` 和前端上限提示；写稿与导演提示按用户要求和内容信息量规划，移除自动写稿的旧 1000 字拒绝条件。保留配音缺失、零/负/非有限时长检查以及实际累计时长统计。

历史超限失败由 `audio_timing.resume_available` 标明可继续，读取时不改写历史。用户点击“继续制作”后沿用原重试机制，保留成功步骤和配音，进入整批配音确认。测试覆盖超过 90 秒、十分钟与数小时的累计时长、原音频复用、正常与测试模式恢复，以及超过 1000 字的自动写稿。部署浏览器验证只读取真实项目与七段音频，不自动触发后续制作。
