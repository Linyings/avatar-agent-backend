# 生产环境技术评估：Go 自研 Agent 与 Pi Agent 框架

日期：2026-11-10
范围：`backend/`（Go API、Agent、工作流）、`backend/avatar-runtime`（Remotion/Python/ffmpeg 渲染）、`deploy/wsl2`。
目标负载：数千到数万注册用户，高峰期并发制作数十到数百条视频。

## 1. 结论

**推荐继续使用 Go，不迁移到 Pi Agent 框架。** 但当前代码在架构上还是单实例 MVP，必须先改造执行架构才能上线。

决定能否上线的不是“用哪个 Agent 框架”，而是下面四件事：

1. 制作任务要从 API 进程里移出去，改成**持久化任务队列 + 独立 worker 池**。
2. 进程内的会话、推送和锁要改成**外部共享状态**，即 PostgreSQL 加 Redis 或 NATS。
3. 素材从本地磁盘迁到**对象存储**。
4. 供应商调用要有**统一的限流、配额和计费**。

Pi 框架解决不了其中任何一项。而 Go 在并发、内存占用、部署和已有的付费安全逻辑上都更适合承担生产负载。

## 2. 两种框架的定位

| | 当前 Go 自研 Agent | Pi Agent 框架（`@earendil-works/pi-agent-core` / `pi-ai`） |
|---|---|---|
| 语言与运行时 | Go，单个静态二进制 | TypeScript / Node.js |
| 定位 | 嵌入在 API 服务里的业务 Agent，工具即后端固定函数 | 通用 Agent 循环库：消息、工具调用、事件流；主要面向编码助手和桌面端的单会话场景 |
| 会话状态 | 进程内 map，并把每条消息写入数据库 | 进程内对象，持久化需要自己实现 |
| 多实例与分布式 | 没有（见第 3 节） | 没有；框架不提供分布式会话、队列和锁 |
| 模型接入 | 自己写的 OpenAI 兼容客户端 | `pi-ai` 统一封装多家模型、流式和工具调用格式，这是它的主要优势 |
| 与现有代码的关系 | 已承载付费订单幂等、积分预留、租约、`FOR UPDATE` 和工作流状态机 | 原 NarratoAI-PC 桌面端使用；Go 版是按它移植的（见 `docs/Agent移植与前端重构开发计划.md`） |

要点：

- **Pi 是“单个 Agent 怎么思考、怎么调用工具”的库**，不是“上万用户的任务怎么调度”的平台。换成 Pi 后，第 3 节列出的阻塞项一个都不会消失。另外还要在 Node 里重写付费订单状态机和计费逻辑，或者跨进程调用 Go，风险更大。
- **Go 更适合高并发 I/O**。在高并发下 Go 的优势比较明确：goroutine 很轻，内存占用低，单个二进制容易做水平扩展，没有 Node 单线程事件循环被 CPU 任务卡住的问题。
- **Pi 值得借鉴的地方**：它对多家模型接口的统一封装和事件流协议设计。可以在 Go 里参考实现，不需要换掉整套运行时。

## 3. 当前代码的生产阻塞项

以下问题都有代码依据，按严重程度排列。

| # | 问题 | 代码依据 | 影响 |
|---|---|---|---|
| 1 | **全局同时只允许一个制作任务** | `avatar_mvp.go:398` `ensureIdle` 统计全库 running 任务，大于 0 就拒绝 | 整个平台同一时间只能做一条视频，这是致命问题 |
| 2 | **所有工作流写操作抢同一把全局锁** | `avatar_mvp.go:365` `pg_advisory_xact_lock(744834291)`，外加 `avatarMVP.mu` 进程锁 | 即使放开第 1 条，所有状态写入仍是串行的 |
| 3 | **渲染、ASR、ffmpeg 和 API 跑在同一个容器** | `avatar_workflow.go:538` 每个阶段 `exec` 一个 Python；Remotion 用 Chromium 软件渲染；Whisper 跑在 CPU；没有并发上限 | 一个重任务就会拖慢 API；之前出现过 WSL 内存不足导致重启 |
| 4 | **进程内状态** | `agent/handler.go:29` 会话 map、`:83` SSE hub；`types.go:154/194` inflight 去重和提案；`preproduction.go:83`；`avatar_workflow_execute.go:24` launch 锁 | 多副本时推送会丢、停止指令无效、去重失效，必须做粘性会话或外部 pub/sub |
| 5 | **租约持有者是常量** | `avatar_mvp.go:34` `avatarOwner = "avatar-server"` | 多副本无法区分谁持有任务；实例宕机不会把任务转交给别的实例，只会标记为中断，等人工重试 |
| 6 | **素材只存在本地磁盘** | `DataRoot` 挂载本地卷；上传和下载都由 Go 进程直接读写 | 任务必须在固定的机器上跑；大文件下载占用 API 的连接和带宽 |
| 7 | **数字人工作流不扣积分，没有配额** | `avatar_workflow.go:306` `BillingStatus: "released"`；`backend/docs/avatar-mvp.md:96` | 对外开放后，用户可以无限消耗付费模型 |
| 8 | **供应商调用没有限流** | 没有令牌桶，也没有按供应商的并发上限；遇到 429 只按临时错误处理 | 高峰期集中触发 RunningHub 的限流，错误会连锁扩散 |
| 9 | **发布要等所有任务排空** | `deploy/wsl2/deployment-guard.py` 有任务在跑就阻止部署 | 每次发布都等于停机 |
| 10 | **可观测性和基础配置缺失** | 没有指标和链路追踪；数据库连接池没设上限；启动时自动迁移；HTTP 服务没有超时，也不支持优雅关闭 | 无法做容量规划和告警；多副本同时启动时迁移会相互竞争 |

已经做得比较好的部分可以直接保留：

- 付费订单状态机：状态不确定时绝不重复提交，恢复时只查原订单。
- 按步骤的输入哈希缓存和订单记录。
- 按行的 `FOR UPDATE` 锁，以及积分预留模型。

## 4. 目标架构（推荐）

```
          ┌─────────── 负载均衡 / Nginx ───────────┐
          │                                        │
     API 副本 × N（无状态 Go）              SSE/WebSocket 网关（也可用 API 副本）
          │   ▲                                    ▲
          │   └──── 事件 pub/sub（Redis Streams 或 NATS）
          ▼
   PostgreSQL（权威状态、积分、订单）  ── 任务队列（River 或 Postgres SKIP LOCKED / Redis）
                                                   │
                ┌──────────────────────────────────┼───────────────────────────┐
                ▼                                  ▼                           ▼
     编排 worker（Go，轻量）           供应商 worker（Go，按供应商限流）        媒体 worker（Node/Python/ffmpeg，按 CPU 限并发）
     推进状态机、分派子任务            提交、轮询付费订单，幂等                Remotion 渲染、ASR、人脸追踪、混音
                │                                  │                           │
                └──────────────── 对象存储（S3/OSS）+ CDN 签名 URL ─────────────┘
```

设计要点：

1. **API 无状态**
   - Agent 对话历史以数据库为准。内存只做缓存，所有副本都从库里读。
   - 同一项目同一时间只允许一个轮次：改用数据库行锁或 Redis 锁，替代现在的进程内 `turnMu`。
   - 推送改用 Redis Streams 或 NATS。客户端带上 `Last-Event-ID`，断线重连后可以补发，不再丢事件。
2. **用队列替代在 API 进程里起 goroutine**
   - 制作任务拆成步骤级的子任务，持久化到队列，由 worker 领取并定期续约。
   - worker 宕机后，租约过期，任务由别的 worker 接手继续执行。付费订单只做查询，不重复提交，现有的订单状态机可以直接沿用。
   - Go 方案建议用 **River**：它基于 PostgreSQL，不需要额外的中间件，支持事务内入队、唯一任务和重试。
3. **租约持有者按实例区分**：用 `hostname + pid + 随机串`；恢复逻辑只处理租约已过期的任务。
4. **去掉全局限制**：取消 `ensureIdle` 和全局 advisory lock，改成三层限流：
   - 每个用户、每个项目的并发上限，例如每个用户最多 2 个任务。
   - 每个供应商的全局并发和速率上限，用令牌桶实现。
   - 媒体 worker 池的大小，按 CPU 核数决定。
5. **媒体计算独立部署**
   - 媒体 worker 单独做镜像，可以按队列长度自动扩缩容。
   - Remotion 的 bundle 在镜像构建时生成一次，不在每个任务里重新打包。
   - Whisper 改为常驻进程或独立服务，避免每次调用都重新加载模型。
6. **对象存储**
   - 素材、成片和中间文件都存到 OSS 或 S3。
   - 下载走签名 URL，经 CDN 分发，不再经过 Go API。
   - worker 本地只放临时文件。
7. **计费与配额**
   - 数字人工作流接入现有的 `CreditReservation`。确认制作时预留积分，供应商返回实际用量后结算，失败时退回。
   - 设置每个用户的每日额度，超额就拒绝。
8. **滚动发布**：API 可以随时重启。worker 收到退出信号后不再领取新任务，等当前步骤完成或续约到期后再退出。这样发布不再需要等全局排空。
9. **可观测性**
   - 指标：OpenTelemetry 加 Prometheus，包括队列长度、各阶段耗时、供应商错误率和 429 次数、每条视频的成本。
   - 日志：结构化日志，统一带上 `run_id`。
   - 配置：数据库连接池设上限；数据库迁移改成单独的发布任务，不在每个实例启动时执行。

## 5. 容量估算

以下是数量级估算，需要压测校准。

| 资源 | 单条 43 秒视频（当前实测） | 100 条并发视频 |
|---|---|---|
| 本地渲染（Remotion，CPU 软件渲染） | 约 3–6 分钟，`--parallel 1` | 约需 100–200 个 vCPU 持续占用几分钟；需要可扩缩的媒体 worker 池，可考虑 GPU 加速 |
| 数字人（Kling Avatar Pro） | 7 段，每段 4–6 分钟，在供应商侧执行 | 约 700 个并发订单，取决于 RunningHub 账号的并发配额，需要与平台确认或申请多个账号 |
| TTS 和 LLM | 秒级，费用很低 | 主要受供应商的速率限制约束，需要令牌桶 |
| API 本身 | 很轻 | 几个 Go 副本即可支撑上万在线连接，SSE 交给专门的网关 |

结论：**瓶颈在本地渲染算力和供应商并发配额，不在 Agent 框架。**

## 6. 实施路线

| 阶段 | 内容 | 收益 |
|---|---|---|
| S1 安全上线门槛（约 1–2 周） | 数字人工作流接入积分和每日额度；按用户和项目限制并发，替代全局只跑一个任务；供应商令牌桶；数据库连接池设上限、HTTP 超时、优雅关闭；基础指标 | 可以小规模公测，比如几十个并发用户 |
| S2 执行与 API 分离（约 2–3 周） | 引入 River 队列；编排、供应商、媒体三类 worker；按实例区分租约；自动接手中断的任务；媒体 worker 独立镜像 | 渲染不再拖慢 API，可以按队列扩容 |
| S3 多副本（约 1–2 周） | 会话、推送和锁外部化（Redis 或 NATS）；SSE 支持补发；对象存储和 CDN；迁移改成单独的发布任务；滚动发布 | API 可水平扩展，发布不停机 |
| S4 容量与成本（持续） | 压测（参考 `backend/docs/PERFORMANCE_BENCHMARK_PLAN.md`）；渲染 GPU 化或预打包；Whisper 常驻；多个供应商账号池与降级 | 支撑数百条并发视频，控制单条成本 |

## 7. 什么情况下考虑 Pi

- 需要快速接入大量不同厂商的 LLM，并统一各家的工具调用格式。
- 产品形态是本地或桌面端的单用户 Agent，例如 NarratoAI-PC。

即便如此，建议的做法也是：服务端仍用 Go 做调度和付费，Pi 只作为可选的“推理子服务”，不承担任务调度、计费或付费订单。
